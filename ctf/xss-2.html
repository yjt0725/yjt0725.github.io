XSS-2

innerHTML의 특징을 이해하고 img onerror로 우회하기

2026.09.16 · yjt0725
Web XSS innerHTML onerror Cookie
이 글은 Dreamhack 워게임 실습 환경에서 공부한 내용을 정리한 기록입니다. 허가받지 않은 웹사이트에는 같은 방법을 사용하지 않습니다.

1. 문제 목표

XSS-2의 목표는 관리자 봇의 브라우저에서 자바스크립트를 실행해 봇이 가진 쿠키를 /memo에 기록하는 것이다.

XSS-1에서 사용했던 <script> 페이로드는 이번 문제에서 작동하지 않았다. 따라서 입력값이 화면에 들어가는 방식을 먼저 분석하고, 다른 실행 방법을 찾아야 했다.

2. 취약점 분석

vuln.html에서는 주소의 param 값을 읽어 다음과 같이 화면에 넣는다.

var x = new URLSearchParams(location.search);
document.getElementById('vuln').innerHTML = x.get('param');

URLSearchParams는 현재 주소의 쿼리스트링을 다루며, x.get('param')은 그중 param의 값을 가져온다. 가져온 값은 innerHTML을 통해 id="vuln"인 영역에 HTML로 삽입된다.

주소의 param 값
↓
URLSearchParams로 읽기
↓
innerHTML로 페이지에 삽입

사용자 입력이 HTML로 해석되기 때문에 XSS가 가능한 구조이지만, 삽입된 모든 태그가 같은 방식으로 동작하는 것은 아니다.

3. script 태그가 실행되지 않은 이유

<script>alert(1)</script>

처음에는 위 코드를 넣어 보았지만 실행되지 않았다. innerHTML로 동적으로 삽입한 <script> 요소는 브라우저에서 실행되지 않기 때문이다.

이는 입력값 전체가 안전해졌다는 뜻은 아니다. 다른 HTML 태그와 그 태그의 이벤트 속성은 여전히 동작할 수 있다.

<script>가 실행되지 않는 것은 별도의 필터가 태그를 삭제해서가 아니라, innerHTML로 삽입된 script 요소의 실행 방식 때문이다.

4. 우회 방법 찾기

이미지가 불러와지지 않을 때 실행되는 onerror 이벤트를 이용했다. 존재하지 않는 이미지 주소를 주면 에러가 발생하고, 그 순간 이벤트 속성 안의 자바스크립트가 실행된다. 

<img src="x" onerror="alert(1)">
부분 역할
<img> 브라우저가 이미지로 처리하는 HTML 태그
src="x" 없는 이미지 주소를 사용해 로드 에러 발생
onerror 이미지 로드가 실패했을 때 자바스크립트 실행

5. 공격 페이로드

<img src="x" onerror="location.href='/memo?memo=' + document.cookie">

src="x"는 이미지 로드 에러를 일부러 발생시킨다.

onerror="..."는 에러가 발생했을 때 안쪽의 자바스크립트를 실행한다.

document.cookie는 이 코드를 실행한 브라우저의 쿠키를 가져온다. 관리자 봇이 실행하면 봇이 가진 FLAG 쿠키가 선택된다.

location.href는 쿠키를 주소 뒤에 붙여 /memo로 이동한다. 그 결과 쿠키 값이 메모장에 기록된다.

6. 플래그 획득 과정

① /flag에 페이로드 입력
작성한 img 태그를 제출한다.

↓

② 관리자 봇이 /vuln 방문
백엔드의 브라우저가 FLAG 쿠키를 가진 채 취약한 페이지를 연다.

↓

③ 이미지 로드 실패
존재하지 않는 src 때문에 onerror가 발생한다.

↓

④ 쿠키를 /memo로 전달
봇이 자신의 쿠키를 쿼리스트링에 붙여 메모 페이지로 이동한다.

↓

⑤ /memo에서 결과 확인
기록된 flag=DH{...} 형태의 값을 확인해 제출한다.

실제 플래그 값은 Write-up에 공개하지 않았다.

7. /vuln과 /flag의 역할

내가 직접 /vuln을 열어 페이로드를 실행하면 내 브라우저의 쿠키만 읽는다. 관리자 봇의 쿠키를 얻으려면 /flag에 페이로드를 제출해 관리자 봇이 취약한 페이지를 방문하도록 해야 한다.

페이지 역할
/vuln 입력한 HTML이 실제로 삽입되고 XSS가 발생하는 곳
/flag 관리자 봇에게 취약한 페이지를 방문하도록 요청하는 곳
/memo 전달된 쿠키 값을 공격자가 확인하는 곳

8. XSS-1과 달라진 점

XSS-1에서는 서버가 입력값을 응답에 직접 포함해 <script> 태그가 실행됐다. XSS-2에서는 브라우저가 입력값을 innerHTML로 삽입하므로 같은 태그가 실행되지 않았다.

결국 취약점이 있다는 사실만 확인하는 데서 끝나지 않고, 입력이 페이지에 들어가는 방식과 브라우저가 각 태그를 처리하는 방식까지 살펴봐야 했다.

9. 방어 방법

innerHTML 사용 피하기

단순히 글자를 보여주는 목적이라면 textContent를 사용해 입력값이 HTML 태그로 해석되지 않도록 해야 한다.

허용할 HTML만 남기기

HTML 입력이 꼭 필요하다면 검증된 정화 도구를 사용해 이벤트 속성과 위험한 태그를 제거해야 한다.

쿠키 보호하기

중요한 쿠키에 HttpOnly를 적용하면 자바스크립트의 document.cookie로 해당 쿠키를 읽을 수 없다.

10. 배운 점

XSS-2를 통해 같은 XSS 문제라도 입력값이 삽입되는 위치와 방법에 따라 사용할 수 있는 페이로드가 달라진다는 것을 배웠다.

특히 <script> 태그가 실행되지 않는다고 해서 XSS가 막힌 것은 아니며, HTML 이벤트 속성도 자바스크립트 실행 지점이 될 수 있다는 점을 확인했다.

11. 핵심 정리

param 값이 innerHTML로 삽입되는 구조를 확인했다. 동적으로 삽입된 script 태그는 실행되지 않았기 때문에, 이미지 로드 실패 시 동작하는 onerror 이벤트로 우회했다. 관리자 봇의 쿠키를 /memo로 전달해 플래그를 확인했다.
